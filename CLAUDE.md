# Chainsmith Android

Native Android client for the Chainsmith Flesh and Blood deck builder. Talks to the `chainsmith` HTTP API (Rust backend, sibling repo). Sister clients: `chainsmith-web`, future iOS.

This repo contains the Android UI, local persistence, the generated API client wrapper, and native UX. No backend code lives here — the validation engine, card data sync, and database are in `chainsmith`.

## Stack

- Language: Kotlin 2.x (K2 compiler), JVM target 17
- UI: Jetpack Compose with Material 3, Compose-only (no XML/Views)
- Architecture: Google's recommended UI / (optional) Domain / Data layers, unidirectional data flow
- DI: Hilt
- Async: Kotlin Coroutines and Flow (StateFlow for UI state, SharedFlow for one-shot events)
- HTTP: Retrofit + OkHttp; models generated by `openapi-generator-cli --generator-name kotlin` from the backend's pinned `openapi.json`
- Serialization: kotlinx-serialization
- Local persistence: Room for structured cache, DataStore Preferences for small prefs, Tink-backed encrypted DataStore + Android Keystore for sensitive material
- Image loading: Coil, loading directly from the LSS CDN URLs the backend surfaces (we do not proxy)
- Build: Gradle KTS with a single `gradle/libs.versions.toml` version catalog, AGP 8.x stable
- Static analysis: ktlint, detekt, Android Lint
- Testing: JUnit 4, MockK, Turbine, ComposeTestRule, MockWebServer

Min/target/compile SDKs (defaults; revisit before the first Gradle scaffold lands):

- `minSdk = 26` (Android 8.0)
- `compileSdk = 35` (Android 15)
- `targetSdk = 35`

## Project phase

**Current phase**: `pre-launch` <!-- Change to `production` when real users have data on devices -->

The phase governs how aggressive the rules in `.claude/rules/` are about backwards compatibility. In `pre-launch` we can rewrite the local Room schema, change UI state shapes, and rename anything. In `production` Room migrations are required for every schema change, persisted UI state shapes are stable contracts, and the API client wrapper has to absorb additive backend changes without crashes.

If you are unsure which phase you are in, read this file. Do not assume.

## Hard requirements (regardless of phase)

- Strict testing discipline. Negative cases and variant coverage are required, not optional. Snapshot or screenshot tests do not count as coverage on their own. If a test fails, investigate before rewriting it. See `.claude/rules/testing.md`.
- Security hygiene from day one. Tokens live in Keystore-backed encrypted storage, never plain SharedPreferences. Gitleaks runs in the pre-commit hook. Dependency advisories block CI. See `.claude/rules/security.md`.
- The generated API client tracks the backend SHA pinned in `.api-version`. Drift between the pinned spec and the generated client is a build failure, not a warning. See `.claude/rules/api-contract.md`.

- `.claude/rules/testing.md`: testing discipline

## Git hooks

Two hooks live in `.githooks/`, wired up by one `git config core.hooksPath .githooks` per clone:

- **`pre-commit`** — scans staged changes for secrets via `gitleaks`, then (if `./gradlew` exists) runs `./gradlew ktlintCheck detekt testDebugUnitTest`. Instrumented and Compose UI tests run in CI, not on every commit. While the Gradle project is not yet scaffolded, the gradle steps are skipped with a notice; the gitleaks step always runs.
- **`commit-msg`** — validates the commit subject line against `.claude/rules/commits.md` (Conventional Commits 1.0). Pure bash, no Node or commitlint dependency.

One-time setup per clone:

```bash
git config core.hooksPath .githooks
```

If `gitleaks` is not on PATH, install it (`winget install Gitleaks.Gitleaks` on Windows, see the [gitleaks readme](https://github.com/gitleaks/gitleaks) elsewhere). The pre-commit hook hard-fails when gitleaks is missing — secret scanning is not optional.

`ktlint` and `detekt` are applied as Gradle plugins, not standalone tools — installation is automatic once the Gradle project lands.

## Common commands

These assume a Gradle project that does not yet exist. They are the targets the rules and the pre-commit hook expect once it does.

```bash
# Build a debug APK
./gradlew assembleDebug

# Run unit tests (no device required)
./gradlew testDebugUnitTest

# Run instrumented tests (requires a connected device or emulator)
./gradlew connectedDebugAndroidTest

# Lint and static analysis
./gradlew ktlintCheck
./gradlew detekt
./gradlew lint

# Regenerate the Kotlin API client from the pinned backend spec.
# Reads .api-version (a single line: the backend commit SHA), fetches
# https://raw.githubusercontent.com/chainsmith-deck-builder/chainsmith/<sha>/openapi.json,
# and writes generated sources under app/build/generated/openapi.
./gradlew :app:generateApi

# Bump the pinned backend SHA after the scheduled job (or you) updates .api-version
./gradlew :app:generateApi && ./gradlew assembleDebug

# Dependency hygiene
./gradlew dependencyUpdates           # Versions plugin
./gradlew dependencyCheckAnalyze      # OWASP Dependency-Check
```

## Definition of done

A change is done when:

- Code compiles with no warnings (treat warnings as errors locally and in CI)
- ktlint, detekt, and Android Lint all pass
- Unit tests pass; relevant instrumented or Compose UI tests pass on at least one emulator
- Negative-path and variant tests exist for the changed code, not just happy-path
- The generated API client matches `.api-version`; if the change required bumping, the bump is in the same PR
- No new advisories from `dependencyCheckAnalyze`
- Manual smoke test on an emulator for any UI change (the only way to catch real recomposition, theming, and motion regressions)

## What lives in this repo vs elsewhere

In this repo:

- Android UI (Compose screens, components, theme)
- ViewModels, use cases (when justified), repositories
- Local persistence (Room, DataStore)
- Generated Kotlin API client wrapper
- Native auth flow (token storage, refresh, deep links)
- Build configuration

Not in this repo:

- Backend HTTP API and validation engine (live in `chainsmith`)
- The OpenAPI spec source (lives in `chainsmith`; consumed via `.api-version` pinning)
- The web client (lives in `chainsmith-web`)
- Card image hosting (LSS's CDN; we link directly, do not proxy)
- Cross-repo issue tracking (use the `tracker` repo in the same org)
